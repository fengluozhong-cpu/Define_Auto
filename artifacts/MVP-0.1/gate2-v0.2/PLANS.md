### 3.1 CTRL-01：任务卡与完成契约

实施及修复任务开始前在 `docs/tasks/<task_id>.md` 或所属阶段已有任务文件维护任务卡，由本文件 §1 索引当前任务，并按 §2 保留阶段到子任务的完整入口；同一任务可以分多次会话执行。只为实际开展的任务建立记录，不预建全部阶段空文件。每张卡至少含以下字段；简单文档任务可在所属任务记录中合并为一条等价记录。

| 字段 | 开始前／关闭时要求 |
|---|---|
| `task_id / baseline_id / authorization` | 任务标识、适用文档／契约版本及已有授权来源；基线尚为 DRAFT 时明确授权边界 |
| `depends_on / reading_record` | 依赖任务、规范／契约／决定的 ID、文件／章节、版本或 hash 及上游产物位置；实际加载范围。按 AGENTS §1 在开始、恢复、审阅、验收时核对，变化后记录重读与影响分析；不能由任务卡漏列而豁免明显适用的规则 |
| `requirements / acceptance_scope` | 关联 G／FR／NFR／AC 及本次验收条款，列明不做和延期部分 |
| `change_scope` | 允许修改的模块／文件和预期变更；超出已授权范围时先评估并按变更控制处理 |
| `fixtures / expected_results` | 固定输入与独立预期的版本／hash、来源和确认人；规则见 REQUIREMENTS 的 CTRL-05 |
| `required_checks / failure_rule` | 验证方法及 `automated`／`manual` 分类和理由、原失败场景及相关回归、通过条件；哪些情况阻断本任务，由谁判断；自动化落地阶段见 §3.2 |
| `actual_changes / evidence` | 实际修改、检查对象版本、执行步骤／时间／结果及证据位置；不能以计划执行替代实际执行 |
| `deliverables / evidence_index` | 本任务的结果、检查证据和拟交付产物分别列明角色、正式路径、版本／hash、状态、关联运行／批准记录及允许的下游用途；不能把上游输入或一次测试报告当作已批准交付 |
| `coverage / findings / deferred` | 对应 CTRL-06 覆盖记录、未决问题、延期批准与补测任务 |
| `review / completion / acceptance` | 所需独立审阅及处理结果，实施者完成声明、指定验收者及判定；业务批准由 Chris 或其指定人员负责 |

任务状态区分 `ready`、`in_progress`、`blocked`、`verification_complete`、`accepted`。实施者在全部适用必需检查通过、证据齐备且无阻断发现后可报告 `verification_complete`；不适用项须按 CTRL-02 确认。所需审阅与验收条件未满足时不得标为 `accepted`。`blocked` 必须记录具体原因、受影响范围及解除条件，可以继续不依赖该阻塞的已授权工作。

固定样本、预期、验收范围或必需检查改变时更新任务卡并保留原因与批准依据；不得在测试失败后静默缩小范围。完整检查证据须保存在对应任务文件或其关联的项目内正式证据位置，正式验收不能只依赖聊天记录或 `work/` 临时文件。

当前及历史任务卡通过 §1／§2 索引访问，不在本节累计任务正文。

阶段结束时，在对应阶段任务文件记录验收汇总：关联子任务及需求范围、成果／证据索引、累计覆盖和质量门结果、未决缺陷／延期／例外、批准对象及验收人／时间／结论。子任务检查通过不自动代表阶段验收通过；延期须记录承接任务或目标阶段，在接收方记录中引用，未确认承接前仍列为原阶段未决项。

### 4.1 CTRL-02：质量门清单、阻断条件与交付状态

每阶段开始前在任务卡或关联记录中冻结质量门清单，由 Chris 或其指定验收负责人确认；包含 `check_id、需求／范围、适用性、是否必需、方法／预期、证据位置、执行结果、阻断发现、判定人`。工具、规则、样本及产物版本须与证据一致。质量门评估记录必须指向该清单及确切快照，不能只填写“已通过”。测试断言结果、被测运行／外部工具状态、质量门判定须分开记录：模拟 P21 不可用且正确阻止批准，可使故障处理测试通过，但目标产物的真实 P21 检查仍为 `not_run`，若为必需项则仍阻止该产物批准。

| 情况 | 判定规则 |
|---|---|
| 当前范围的必需检查为 `failed`／`not_run`，或因环境问题无法执行 | 阻止该任务／阶段验收及相关产物批准；允许保留明确标注缺口的草稿 |
| 必需测试未被收集／被跳过、应执行套件为零用例，或测试执行错误 | 不能记为通过；按对应检查的 `not_run`／`failed` 记录并阻止验收，不能仅依赖命令退出码 |
| 声称 `not_applicable` | 须有适用性依据及指定验收负责人确认；工具不可用、输入不足或执行失败不能据此改成不适用 |
| 存在阻断缺陷、关键未决语义、失效裁决／批准或缺失证据 | 维持 `blocked`／待审阅；解释文字不能替代修复、重测或有效裁决 |
| 非阻断问题申请接受例外 | 按 CTRL-06 记录风险及人工批准，保留原始发现；可以作“带已批准例外的验收”，不能写成全部测试通过 |
| 必需范围确需调整 | 先记录影响、原失败／未运行结果并获对应变更批准，明确延期与补测，再按新范围判定；不得为规避失败临时降级必需项 |

产物状态与任务状态分别保存：

- `draft`：可以含未知、缺口或失败结果，用于检查与迭代。
- `review_ready`：审阅材料、来源、当前检查结果和未决清单齐备；表示可以开始审阅，不表示必需检查全通过或阶段验收完成。
- `approved`：当前范围的全部适用必需检查通过，所需独立审阅完成，阻断项已关闭，非阻断例外已获明确批准；Chris 或其指定人员批准确切的模型／依赖／产物快照，文档基线按 CTRL-03 绑定文件快照。

生成成功不会自动改变交付状态。阶段验收也必须符合其质量门，不能由 `review_ready` 直接推定；批准只对记录的用途及范围有效，不自动授予发布或监管递交授权。依赖变化时按 ARCHITECTURE 的 CTRL-04 标记受影响结果为需重审，保留历史状态。

### 6.1 CTRL-03：可恢复基线与批准绑定

首次及每次基线批准时，保存不可覆盖的版本目录或 ZIP。建议位置为项目内 `baselines/<baseline_id>/`，其中包含实际批准范围的规范文件及必要引用文件，不限于五份入口文档；manifest 列明相对路径、文件角色／批准范围、各自版本、字节数与 SHA-256。拆出的规范正文、适用任务契约和验收证据不能只留下指向可变工作文件的链接。任务验收还须绑定任务卡、契约、输入／独立预期、被测版本和实际证据快照；较大证据可引用另存的不可覆盖快照并核验可恢复性。批准记录另存，记录 `baseline_id、manifest hash、快照位置、批准范围／保留项、批准人、批准时间及授权来源`；单有文件 hash 而无文件副本不构成可恢复快照。

快照保留目录关系，并能将正文引用解析到 manifest 中的对应副本；不得在恢复时误读工作区当前版本。外部标准／调研只固定本次相关的来源、版本、定位与 hash，获许可时保存必要副本，不自动复制整个知识库；若必要依据无法取得或恢复，记录缺口并阻止依赖该依据的验收。内容迁移后更新当前引用和迁移索引，历史已批准快照不回写。

执行顺序为：固定待批准内容并制作快照／manifest -> 核验可以逐文件读取且 hash 匹配 -> Chris 针对该快照批准 -> 在快照之外追加批准记录 -> 更新当前 PLANS 中的指针与状态。为避免自引用，manifest 不包含其自身和后加的批准记录；快照内 PLANS 保留冻结时内容，当前 PLANS 的批准更新不回写快照。批准后内容变化须使用新 baseline_id，不替换原文件。

批准有保留项时明确哪些条款暂不生效；需要改正文的，先形成新快照再批准。后续如获 Git 授权可用可恢复的提交标识辅助保存，但本规则不自动授权提交或回滚。本段在 v0.2 建立机制；本次实际批准记录为 [APR-20261020-01](E:/Initiation/Define_Auto/docs/approvals/APR-20261020-01.md)，原始快照保持不变。
