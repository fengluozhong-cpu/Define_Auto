## 1. 状态与证据口径

- **User-stated**：当前请求、可读取的历史用户正文直接表达的需求。
- **Proposed**：本轮技术判断或建议，需相应批准后作为实现约束。
- **Verified-local**：本轮重新读取／计算得到的本地事实，仅对指定文件快照成立。
- **Verified-doc**：本轮读取的一手官方文档所支持的能力描述，不等于本机已运行成功。
- **Historical**：既有报告／对话记录的事实主张，本轮未复现；保留来源和日期。
- **Open**：缺证据或缺用户业务决定，不得作默认事实。

官方文档是一手规范来源；不沿用旧证据日志将所有官方文档归为“二手”的分法。机器可读字段、自然语言语义与端到端可运行能力分别评估。

### 6.1 CTRL-05：独立预期与风险相称的独立审阅

- 在实现对应逻辑前，为关键用例固定输入样本及其 hash、预期事实／差异／输出、预期来源位置和审阅人。业务预期由 Chris 或其指定人员确认；可由 Agent 起草，再依据原始输入及适用规范独立复核。
- 被测实现产生的结果只能作为实际结果，不能直接充当标准答案。人工推导、固定的已审阅示例或经独立验证的参考方法可作为预期来源；若使用与实现共享的解析或计算逻辑，须说明共同失误风险并增加独立检查。
- 预期变更需记录原因、来源证据、影响用例及重新批准；保留旧预期和旧失败结果，不能为让测试通过而同步改变答案。Task 001／GATE-1 冻结首批预期，其余模块在实现前按同一规则补齐。
- 核心比较、对象身份、来源权威、No Data／VLM／CodeList 语义、patch 及生成转换逻辑的变更，在任务关闭前须由实施者之外的审阅者检查需求对应、边界／失败场景、差异及实际验证证据。可以是独立审阅 Agent 或人员；记录审阅对象版本、发现与处理结果。普通低风险文档编辑采用相称检查，不要求逐项独立审阅。
- 实施者提交“修改及检查完成”；任务卡指定的审阅者确认技术关闭条件。业务语义、接受例外和最终交付批准由 Chris 或其指定人员决定，独立 Agent 的审阅结论不能代替这些批准。

| 记录字段 | 要求 |
|---|---|
| 需求／验收条款与任务 | 使用 FR／NFR、具体条款及 task_id；一条需求可对应多个用例 |
| 用例与预期 | 用例 ID、固定输入／预期版本、正例／反例／边界／回归的适用范围 |
| 实际执行证据 | 自动／人工分类；检查步骤或可重复执行入口、实际选中及执行的用例 ID、未收集／跳过项、运行环境／配置、执行时间、实际结果及正式证据位置，关联被检查版本、输入／预期及依赖快照；相关对象或依赖变化后旧通过记录不能自动视为当前通过 |
| 覆盖状态 | `not_covered`／`partial`／`covered`；覆盖状态与检查是否通过分别记录 |
| 未覆盖与延期 | 具体缺口、原因、影响、批准范围及补测任务／阶段；未批准延期不能被计入当前验收通过范围 |
| 结果与审阅 | `passed`／`failed`／`not_run`／有依据的 `not_applicable`，相关发现／例外 ID 及审阅结论 |

“适用子集”须列出具体场景和未覆盖部分；部分覆盖不能报告整个需求已通过。输入、规则或输出链路改变后，更新受影响的回归与跨产物检查。NFR 同样必须映射到相称的检查，不能因没有单独 AC 编号而遗漏。

缺陷与例外至少记录 `finding_id、关联需求／用例、影响对象及版本、严重性、原始证据、责任人、处理状态`。严重性采用两档：**阻断**表示影响本次必需验收条件、关键语义、溯源或数据保护；**非阻断**表示不影响这些条件且风险已有明确说明。影响未知时先阻断相关验收，待评估后再定级；不能因实现困难而降级。

最小生命周期为 `open -> in_progress -> ready_for_retest -> closed_fixed`；依赖变化或复测失败可进入 `reopened`。修复关闭必须关联具体修订、原失败场景重测、受影响回归及审阅确认；仅有解释文字、代码改动或一次无关测试不能关闭缺陷。技术修复可由指定独立审阅者确认，涉及业务语义的修复还须相应业务确认。

`accepted_exception` 是独立处理状态，须记录理由、影响范围、剩余风险、批准人／时间和复评触发条件；不能改写为 `closed_fixed` 或测试 `passed`。它仅能按 PLANS 的 CTRL-02 处理非阻断问题，不能豁免必需检查失败或未运行。若需求或验收范围确需改变，先走变更控制，保留原失败、延期及批准记录，按新范围重新评估。

自动化测试的最低落地阶段见 PLANS §3.2；零用例／漏收集／跳过必需项及三层结果判定遵循 CTRL-02，不能把故障注入测试通过写成实际产物的外部验证通过。

工具执行失败、发现业务差异、软件缺陷和接受例外分别记录；报告问题被解释不等于产生该问题的软件行为已经修复。当前 Task 000 只定义上述规则，实际用例与软件验证在相应实施阶段执行。

## 8. 范围排除与防漂移

Task 000 不实现系统、不创建新服务、不申请账户／Key、不安装环境、不下载真实研究资料、不修改外部知识库。长期保留 ADaM／ADRG、Protocol／SAP 与数字化方案扩展。旧“只做审阅”“暂不做 ADaM”的范围不能覆盖当前用户目标。需求新增、删除或改变验收须关联变更 ID 与批准记录。
